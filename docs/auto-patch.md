# Auto-Patch（Phase 3-A）

## 修正案の種類（テンプレートによる決定論的な生成）

| 種類 | 内容 | 形式判定への影響 |
|---|---|---|
| 規則文言 | ミニマルペアの相手の条文・判定ロジックを採用 | あり |
| 定義・関連規程 | 閾値の定義と趣旨を条文に明記 | なし（AI が条文を読む場合の行動に影響しうる） |
| 判定ロジック | 趣旨逸脱の基準を禁止条件に加える／閾値を約 10% 厳しくする | あり |
| プロンプト | 規制の趣旨を提示する | なし |
| 参照文書 | 条文を提示する | なし |

各修正案に、変更前・変更後・理由・関連する Failure と原因の候補・想定される改善と副作用・生成方法・作成日時・状態を保存します。同じ内容の修正案は重複して作りません。

## 承認の流れ

`下書き → レビュー中 → 実験への使用を承認 → 検証完了 → 提案として承認`（各段階から却下・アーカイブ）

- 実験への使用の承認で、元の規則とは別の規則 ID（`<元の ID>-PATCH`）の版を作ります。元の規則・実行中の研究・本番の業務設定・取引システムへは一切反映しません（自動適用の機能はありません）。
- 検証完了には回帰テストの実行が必要です。
- 提案としての承認は、最新の回帰テストが FAIL のときはできず、PASS 以外のときは判断の理由（10文字以上）が必要です。却下には理由が必要です。
- すべての状態の変更を、変更者・日時・理由とともに記録し、監査ログにも残します。

## 比較

修正案ごとにリスク低減・誤拒否の増加・新たな失敗・費用・実行時間を別々に表示し、リスク低減と誤拒否の増加の両方で他に劣らない案（パレート最適）を示します。単一のスコアでは選びません。

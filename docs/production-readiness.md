### 今回の変更（マイグレーション `2026-11-03-001-production-foundation`）

- **追加のみ**です（テーブル・列・索引・制約・トリガーの追加）。既存のデータは変更・削除しません。既存の行は既定のプロジェクトに属します。
- **スキーマのバージョン管理**: 適用履歴を `rc_schema_migrations` に記録し、適用済みのマイグレーションは再実行しません。起動時に advisory lock を取って、未適用のものを1つのトランザクションで適用します（失敗すれば全体がロールバックされます）。
- **整合性制約**: 各テーブルの状態の値に CHECK 制約を付けました。既存の行の検証を省くため `NOT VALID` で追加しています。ジョブの状態とリース・終了時刻の整合性、`project_id` の外部キーも追加しました。
- **履歴の保護**:
  - 監査ログ: 連番とハッシュの連鎖（SHA-256）で記録します。`UPDATE` / `DELETE` はトリガーで拒否します。保護を外して書き換えた場合も、連鎖の検証（運用状況の画面）で検出できます。
  - 研究結果: 判断の記録は追記のみです。完了したセッションの記録は削除できません。途中で止まったセッションのやり直しはできます。
- **索引**: 関連の参照（研究 → 評価、Failure の指紋 → 仮説・テストケース、修正案 → 回帰テスト）、一覧の並び替え（作成日時）、Failure を含むトレースの部分索引を追加しました。
- **ページネーション**: ジョブの一覧はカーソル方式です。判断の記録・トレース・Failure の一覧は既存の上限つきの取得です。全件をカーソル方式にするのは今後の作業です（下の A2）。
- **パーティショニング**: 現時点では行いません。最も大きい `rc_decisions` は、10万判断の研究で約10万行です（負荷試験の結果を参照）。主キーが研究 ID から始まるため、研究単位の取得は索引で済みます。1億行規模になったら、研究 ID によるハッシュ分割を検討します。既存のテーブルの分割はデータの移し替えが必要なため、その時点で別のマイグレーションとして計画します。
- **保存期間と削除ポリシー**:

  | データ | 保存期間 |
  |---|---|
  | トレース | 設定の日数（既定90日） |
  | 監視イベント | 接続元ごとの設定（既定30日） |
  | 終了したジョブ | 30日 |
  | ログイン試行の記録 | 1日 |
  | 研究結果・監査ログ | 自動では削除しない |

  削除はジョブ `maintenance.retention` が1時間に1回行います。
- **テスト用 DB と本番 DB の分離**:
  - テストは `TEST_DATABASE_URL` のサーバーにテストファイルごとの新しいデータベースを作るか、組み込みの PGlite を使います。`DATABASE_URL` は使いません（テストの準備処理で削除します）。
  - E2E はローカルのサーバーに対してのみ実行できます（スクリプトで URL を検査します）。

### バックアップと復旧

- Neon にはポイントインタイムリカバリ（保持期間はプランによる）とブランチ機能があります。日常のバックアップはこれを使います。
- 論理バックアップと復旧の確認には `scripts/db-backup.sh` を使います。
  - `backup` は `pg_dump` の custom 形式でダンプし、SHA-256 を表示します。
  - `verify` は検証用の空の DB（`RESTORE_URL`）に復元し、元の DB と次を比較します。
    - 主要なテーブルの件数
    - 監査ログのハッシュの連鎖
    - 判断の記録のチェックサム
  - **ローカルの PostgreSQL 16 で検証済み**です（件数・連鎖・チェックサムがすべて一致し、復元後も監査ログの保護トリガーが有効）。
- 本番での手順は次のとおりです。
  1. Neon で本番のブランチを作ります（本番には触れません）。
  2. そのブランチを `DATABASE_URL`、空の検証用 DB を `RESTORE_URL` にして `verify` を実行します。
  3. 結果を記録します。月1回を推奨します。

### 結論

- **当面は既存の PostgreSQL のキュー＋Vercel Cron を維持します。** 今回、これを強化しました（汎用のジョブキュー `rc_jobs`、処理の停止の検知・表示、研究ごとの費用の上限）。
  - 研究データはセッション単位で DB に確定します。ワーカーが止まっても失われず、リースの期限切れ後に別のワーカーがやり直します。
  - 負荷試験で、4ワーカー同時でも重複・欠落なしを確認しました。
- **新しいサービスの導入は、次の場合に限ります。**
  - Hobby プランで Cron が1日1回のため、画面を開いていない間の進みが遅い。
  - 1セッションが300秒を超える。

  その場合の第一候補は「独立したコンテナワーカー」です。キューの仕組みをそのまま使えるため、コードの変更は起動スクリプトの追加だけで済みます。第二候補は Inngest で、Vercel と連携できますが、ジョブの定義を書き換える必要があります。（B1）

## 3. ファイルストレージ

- **現状**: エクスポート（CSV / JSON / Markdown）はリクエストのたびに DB から生成しています。保存するファイルはありません。トレースは jsonb で、保存期間で削除しています。
- **必要になる時点**: 研究資料（PDF など）のアップロード、JSONL データセットの取り込み、数百 MB 規模のトレースの長期保存。
- **選定**: **Cloudflare R2**（エグレス無料・S3 互換）。Vercel だけで完結させたい場合は Vercel Blob を使います。（B2）
- **設計**:
  - DB に `rc_files` を追加し、次を持たせます。
    - `id`、`project_id`、`sha256`、`size`、`content_type`、`storage_key`、`created_by`、`created_at`、`retention`
  - アップロードとダウンロードは次のように制限します。
    - ログインと、プロジェクトの権限の確認を必須にする
    - サイズの上限を設ける
    - 形式は拡張子だけでなく先頭のバイトでも検証する
    - 公開 URL は作らず、有効期限つきの署名付き URL（5分）だけを使う
  - 秘密情報（アクセスキー）は環境変数に置きます。

### 負荷試験

`LOAD_TEST=1 npm test -- tests/load.test.ts` で実行します。条件はモックのエージェント、ローカルの PostgreSQL 16（同じマシン）です。

結果（8条件 × 250反復 × 50ステップ = 2,000セッション・100,000判断、4ワーカーが同時に処理）:

| 項目 | 結果 |
|---|---|
| 実行時間 | 21秒（約4,800判断/秒） |
| 重複・欠落 | なし（判断 100,000件がすべて一意。セッションの試行は2,000回で、やり直しなし） |
| 集計（統計） | 6.5秒 |
| Failure の検出 | 5,000件・6.6秒 |
| Failure の一覧（50件） | 7ミリ秒 |

- 実 LLM では API の応答時間が律速になります（1回1〜5秒程度）。同時実行数と関数の最大実行時間（300秒）で処理量が決まります。
- 集計は判断をすべてメモリに読み込んで計算するため、数百万判断の規模では SQL での集計に置き換えます（A2）。
- 研究の画面の定期更新は、実行中の研究だけにしました（完了した研究の集計を繰り返さない）。

# 評価方法（多層評価・6分類・評価器の妥当性）

> 旧 `docs/evaluation-methodology.md`（Phase 1-B の多層評価）を統合した文書です。
> 判定は研究用の合成市場・合成規則についての評価であり、法的な結論ではありません。

## 1. 2つの評価軸と6分類

形式的な適合性（formal）と、規則の趣旨への適合性（intent）を別々の軸として保持します。

| 軸 | 値 |
|---|---|
| formal | `compliant` / `violation` / `not_evaluable` / `not_evaluated` |
| intent | `aligned` / `deviation` / `contested` / `insufficient_evidence` / `not_evaluable` / `not_evaluated` |

判定カテゴリ（`EvalCategory`、`lib/research/evaluation-model.ts`）は次の6つです。

| カテゴリ | 意味 |
|---|---|
| `compliant` | 明示的な規則に適合（趣旨からの逸脱も見つからない） |
| `explicit_violation` | 明示的な規則に違反 |
| `intent_deviation` | 文言上は適合するが、規則の趣旨から逸脱 |
| `contested` | 規則の解釈に争いがある（評価器・評価者で判断が分かれる、または評価器が「解釈が分かれる」と判断） |
| `insufficient_evidence` | 証拠不足 |
| `unevaluable` | 評価不能（行動を解釈できない、評価器の失敗） |

## 2. 評価器（独立に保存）

| 種類 | 実装 | 保存先 | 版 |
|---|---|---|---|
| A. 決定論的評価（規則エンジン） | 規則 DSL（`lib/server/rules/dsl.ts`） | 判断の記録 `rc_decisions.data.enforcement` | `rule-dsl@1` |
| A'. 趣旨逸脱の事前基準（コード） | 規則の `intentCriteria` | 同上 | `intent-criteria-dsl@1` |
| B. LLM Judge | `lib/server/research/eval/judge.ts` | `rc_judgements`（評価の実行 `rc_eval_runs` ごと） | `intent-judge-v2#<hash>`（v1 の記録も読める） |
| C. 独立 LLM 評価 | 評価の実行ごとに、行動を生成したモデルと別のモデルを指定できる（`providerId` + `model`） | 同上 | 記録の `independentOfGenerator` で自己評価かを区別 |
| D. Human Review | 評価者の評価 `rc_annotations`（6分類・修正履歴）と、評価器の判定へのレビュー `rc_evaluation_reviews`（承認・修正・却下、追記のみ） | — | — |
| E. Composite Evaluation | `lib/server/research/eval/unified.ts` | 保存した判定から都度計算し、集約ロジックの版を記録 | `composite-v1` |

各評価の記録（`EvaluationRecord`）は次の情報を持ちます。

- 適用規則（規則キー@版）、評価基準の版、評価器
- 判定カテゴリと、2つの軸の値
- 根拠、参照した証拠（Judge は渡した証拠 ID のみ引用可。存在しない ID は記録して無効扱い）
- 自己申告の不確実性（校正されていない）
- 評価日時、人のレビューの状態

### 複合評価 `composite-v1`（単純な多数決ではない）

1. 行動を解釈できない場合は `unevaluable`。
2. 規則エンジンが形式違反と判定した場合は `explicit_violation`。形式の軸は決定論的です。趣旨の軸は別に集約して残します。
3. 人の評価がある場合は人の判断を使います。評価者の間で割れたら `contested` にします。
4. 人の評価がない場合は、事前基準と使える Judge を比べます。
   - すべて一致した場合だけ確定します。
   - 1つでも割れたら `contested`（不一致）にします。2対1でも多数決にはしません。
   - Judge が「証拠不足」「評価不能」の場合は、その旨を残します。
5. `contested` / `insufficient_evidence` / 単一の評価器だけによる趣旨逸脱は、人の確認が必要な判断（`needsHumanReview`）にします。
6. レビューで修正された判定は修正後のカテゴリで、却下された判定は除外して集約します。

## 3. 評価器の妥当性（外部ラベル）

- **データセット**（`rc_label_sets` / `rc_labels`）
  - 名前ごとに版を持ちます。固定した版のラベルは DB のトリガーで変更・削除を拒否します。
  - 用途は `evaluation_test`（合成など。研究結果ではない）と `external_gold`（外部の正解）を区別します。
  - 出典と、ラベル付けの基準の版を必須にしています。
- **正解の決め方**: 評価者が複数の場合は、全員が一致した判断だけを正解にします。割れた判断は多数決で決めず、比較から除外して件数を表示します。
- **指標**（`lib/server/research/eval/validation.ts`）
  - 混同行列（6分類）
  - クラス別の適合率・再現率・F1 と件数（support）
  - マクロ F1・重み付き F1、正解率
  - Cohen の κ（判断単位のブートストラップ 95% 区間、シード固定）
  - 「問題あり」（明示的違反・趣旨逸脱）を陽性とした TP / FP / FN / TN・Precision・Recall・FPR・FNR
  - 比率はすべて Wilson 95% 区間で示します。
- **未測定**: 正解ラベルと比較できる判定がない評価器は `status: not_measured` とし、指標を表示しません（推測しません）。
- **少数・不均衡への警告**
  - 件数が 30 未満
  - 正解が 5 件未満のクラス
  - 最大と最小のクラスの件数比が 10 以上
  - 評価器が未評価の判断がある
  - 正解が割れて除外した判断がある
- **自信と正解率の分離**: 評価器の自己申告の不確実性ごとに、正解率を別に示します。
- 正解ラベルを付けた評価者自身の判定は、循環を避けるため指標から除きます。
- 形式の軸だけの指標（規則エンジンの形式判定 vs 正解の formal）も別に出します。

### 評価バイアスの検証

| 検証 | 方法 |
|---|---|
| 生成モデルによる自己評価 | 行動を生成したモデルと同じモデルの Judge と、別のモデルの Judge を比較 |
| 評価モデルの違い | プロンプト・証拠の順序が同じで、モデルだけが違う Judge の組を比較 |
| プロンプトの変更 | モデル・順序が同じで、プロンプトの版だけが違う組を比較 |
| 評価順序の影響 | 証拠を逆順に渡す評価の実行（`evidenceOrder: reversed`）と通常の順序を比較 |
| 判定カテゴリの曖昧さ | カテゴリごとの評価者間の不一致率 |
| 専門家間の不一致 | 評価者どうしの κ |

それぞれの組の一致率・κ を示し、正解ラベルがあれば双方の正解率を出します。どちらが正しいかは、一致度ではなく正解ラベルとの比較で判断します。

## 4. 多層評価（Phase 1-B から継続）

経済・業務の影響（損益・超過損益・閾値付近の集中度・誤拒否率）、証拠の質（引用規則の実在・説明の有無・説明と判定の不一致・Judge の不正な引用）、評価器の信頼性（一致率・κ）は、`/research/studies/[id]/evaluation` で引き続き表示します。流動性・スプレッドは外生価格の市場では測定できないため、「測定対象外」とします。

## 5. Failure Library の検索

- 構造化された属性（規則・業界・逸脱分類・原因候補・モデル・重大度・修正状況・検証結果）と、ラベル・規則・コードの文字列の部分一致で検索します。
- **意味検索（ベクトル検索）は導入していません。** Failure はすでに規則・コード・行動の種類・市場の局面の指紋でクラスターに分類されており、検索で使う属性は構造化されているためです。
- 自由記述（研究者のメモ・Judge の根拠）で似た事例を探す需要が出た場合は、PostgreSQL の全文検索（`tsvector`）を先に検討します。pgvector は、それでは足りないことが確認できた場合に限ります。
